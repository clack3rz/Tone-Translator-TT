SECTION 1 — EXECUTIVE SUMMARY
--------------------------------------------------------------------------------

1.1 AUDIT SCOPE & METHODOLOGY
This audit evaluates the current tone-engineering knowledge, provenance, and
decision-making mechanisms within Tone Translator (TT). The investigation was
conducted strictly as a read-only repository inspection. No application code,
system prompts, test suites, or Firestore records were altered. No Gemini API
calls were executed for dynamic testing.

The audit traced the complete current decision path from user inputs to final
preset export, evaluating:
  - Application input handling and dropzone wiring (/src/App.tsx)
  - Tone profile taxonomic classification (/src/services/toneProfileBuilder.ts)
  - System prompts, amplifier and cabinet directories, and validation recipes
    (/src/services/geminiService.ts)
  - Post-generation deterministic mutations, pedal swapping, and noise gate
    calibration (/src/services/geminiService.ts)
  - Semantic microphone placement reasoning and multi-mic blending engines
    (/src/services/at5MicPlacementReasoning.ts, at5MicPlacementService.ts)
  - Hardware normalization, rack/stomp EQ deduplication, and signal chain
    structural cleanup (/src/services/at5SignalChainNormalizer.ts)
  - Parameter serialization and VIR coordinate translation
    (/src/services/presetExporter.ts, at5ParameterManifest.ts, at5VerifiedProtocols.ts)
  - Static validated profiles and knowledge bases
    (/src/knowledge/validatedToneProfiles/acdc_jailbreak_malcolm_young_studio.json,
     /src/services/at5AmplifierKnowledge.ts, /src/services/at5CabinetKnowledge.ts)
  - Architectural Sound Engineer domain contracts and schemas
    (/src/types.ts, /src/sound-engineer/*)

1.2 OVERALL ARCHITECTURE OBSERVED
Current TT tone generation operates not as an autonomous, general-purpose AI
Sound Engineer reasoning from foundational acoustic first principles, but rather
as a hybrid, multi-stage pipeline:
  1. Front-End Taxonomy (AI or Static Recipe): Pre-classifies style, role, gain,
     and hardware families.
  2. Prompt-Augmented Generation (AI): Injects curated directories of specific
     AmpliTube 5 gear, rules of thumb, and strict negative constraints into a
     Gemini 3.8 Flash prompt to emit an initial AT5 signal chain.
  3. Post-Generation Deterministic Surgery (Code): TypeScript logic inspects prompt
     keywords and signal chain elements, overriding pedals (OverScream vs.
     PROdrive), recalibrating noise gate timing/thresholds, forcing specific
     semantic mic placements (position, distance, angle), and rewriting the
     generated engineering notes.
  4. Platform Normalization & Serialization (Code): TypeScript logic maps gear
     names to AT5 GUIDs, deduplicates EQs based on functional slot rules, and
     translates semantic parameters into XML attributes.

1.3 MAJOR SOURCES OF CURRENT TT ENGINEERING BEHAVIOUR
Engineering behaviour in TT originates from four distinct layers:
  - Deterministic Application Code (Dominant for critical behaviours): Hardcoded
    TypeScript logic makes the final decisions regarding boost pedal insertion,
    noise gate thresholds/decay times, microphone position/distance/angle, and
    EQ deduplication.
  - AmpliTube 5 Platform Specifications (Heavily coupled): Knowledge of AT5-specific
    gear names, knob parameter names, XML attributes, GUIDs, and 2-band limits on
    Parametric EQ dictates much of what appears to be "engineering advice".
  - Curated Static Recipes (High reliability on key benchmarks): Fixed presets
    and keyword intercepts for Malcolm Young / AC/DC, Metallica Kill 'Em All,
    and Pantera Cowboys From Hell bypass AI reasoning when validation mode is
    active or when static recipes match.
  - Gemini / LLM Intrinsic Capabilities (Constrained): Gemini performs semantic
    matching between user prompt keywords and the curated AT5 amplifier/cabinet
    directories, but its autonomous reasoning is heavily policed and frequently
    overridden by downstream code.

1.4 IMPORTANT PROVENANCE OBSERVATIONS
  - Distinction between "Producing an outcome" and "Understanding a principle":
    TT consistently produces professional-looking signal chains (e.g. cutting
    bass before high-gain distortion, placing an OverScream before a Brit 8000),
    but the system does not derive this from acoustic modeling or dynamic causal
    reasoning. It applies deterministic heuristics ("if thrash -> OverScream
    Level 9 Drive 1") and template rules.
  - Complete decoupling of UI inputs: The "Your Recording" (currentAudio) dropzone
    is accepted by the UI, converted to base64, passed into translateTone(),
    and then silently ignored—never sent to Gemini or analyzed by DSP.
  - Placeholder audio metrics: All nine audio feature extraction fields on
    ToneProfile (spectral_centroid, low_end_tightness, etc.) are explicitly
    overwritten with `undefined` in toneProfileBuilder.ts.
  - Disconnect between contract vocabulary and runtime execution: Extensive domain
    contracts created in Phase 1B (EvidenceRecord, EngineeringDecisionRecord,
    SemanticToneDesign) exist only as type definitions and synthetic trace fixtures;
    they do not execute during Current tone generation.

1.5 LIMITATIONS OF STATIC REPOSITORY ANALYSIS
Static inspection definitively reveals code paths, prompt contents, data schemas,
and deterministic overrides. However, static inspection cannot prove whether
Gemini internally "understands" sound engineering concepts when prompted without
constraints. Claims regarding Gemini's intrinsic model capabilities are therefore
classified as "Potentially model-intrinsic; not verifiable from repository
evidence alone."

SECTION 4 — GEMINI PROMPT KNOWLEDGE INVENTORY
--------------------------------------------------------------------------------

4.1 EXPLICIT ENGINEERING PRINCIPLES SUPPLIED TO GEMINI
Inspection of `MASTER_PROMPT` in `/src/services/geminiService.ts` (lines 19-269)
reveals the following engineering principles explicitly communicated to Gemini:
  1. Gain Pivot Architecture:
     - Pre-Gain (Input stage): Shaping behaviour (Wah, Compressor, Mid-boosters,
       EQ to tighten low end before nonlinear stages).
     - Post-Gain (FX Loop / Rack): Refining tone (EQ for mix balance, modulation
       for clarity, delay/reverb for spatialisation).
  2. Gain Staging Discipline:
     - Distribute gain incrementally across stages; never max out a single stage.
     - Use clean boost with high level and low drive to tighten high-gain inputs.
  3. Frequency Dominance:
     - The electric guitar is fundamentally a midrange instrument.
     - Metal: Moderate mid-scoop (bands 2-4) compensated with post-gain presence.
     - Rock: Forward midrange focus (bands 6-8) for projection.
  4. Causal Troubleshooting Heuristics:
     - Muddy tone -> Reduce bass PRE-distortion.
     - Harsh/fizzy tone -> Reduce treble/presence POST-distortion.
     - Lost in mix -> Boost midrange (700 Hz - 1.5 kHz).
     - Cluttered delay -> Synchronize to tempo and position in FX Loop/Rack.
  5. Impedance & FX Order:
     - Fuzz pedals must precede buffers for proper passive pickup impedance loading.
     - Reverb must follow delay so delay repeats are properly spatialized.

4.2 INSTRUCTIONS, HEURISTICS & NEGATIVE CONSTRAINTS
  - Negative Constraints: Explicit lists forbidding modern high-gain amps,
    rack EQs, or modulation for classic rock requests (e.g. AC/DC Malcolm Young).
  - Control-Aware Generation: Gemini is strictly instructed to generate ONLY
    parameters that physically exist on the selected amplifier model in
    `AT5_AMPLIFIER_KNOWLEDGE`, baseline settings from `typicalSettings`, and
    never invent knob names.
  - Multi-Mic Role Rules: Explicitly mandates assigning distinct roles
    (e.g., Dynamic 57 for attack, Ribbon 121 for warmth/fizz control).

4.3 REQUESTED REASONING VS. REQUESTED OUTPUTS
  - Requested Outputs: RFC 8259 JSON containing `tone_summary`, `signal_chain`,
    `engineering_notes` (`gain_strategy`, `noise_control`, `eq_strategy`,
    `amplifier_debug`, `microphone_debug`), `confidence`, `tone_adjustment_intent`,
    and `rack_decision`.
  - Nature of Requested Reasoning: Gemini is asked to "explain why the selected
    amp was chosen over others" and "document systematic reasoning (style,
    low-end requirements, cabinet construction, speaker family)".
  - Limitation: The prompt asks Gemini to write *explanations after selecting gear*
    rather than execute an evidence-based diagnostic or trade-off evaluation loop.

4.4 SUPPLIED KNOWLEDGE VS. REQUESTED REASONING
  - Supplied TO Gemini: Complete catalog of 30+ amps with knob lists and ranges,
    detailed cabinet construction rules, speaker descriptions, mic placement
    formatting rules, and genre templates.
  - Requested FROM Gemini: Pattern matching between user prompt keywords and
    the supplied catalog, followed by text justification in debug fields.

SECTION 5 — DETERMINISTIC ENGINEERING BEHAVIOUR INVENTORY
--------------------------------------------------------------------------------

This section catalogues application TypeScript code that makes substantive
tone-engineering decisions independently of, or by overriding, Gemini:

--------------------------------------------------------------------------------
1. Thrash Boost Pedal Override & Injection
- File & Symbol: /src/services/geminiService.ts: adjustThrashPedalSelection()
- Trigger: User prompt matches thrash/metal keywords OR Gemini selected a Marshall-family amp.
- Decision: Overrides any distortion/overdrive pedal to "OverScream", or injects "OverScream" before the first amp if no boost exists. Sets Drive to 1.0 (or 4.5 for raw thrash) and Level to 9.0 (or 6.5). Overwrites engineering notes text.
- Engineering Effect: Enforces pre-distortion low-end roll-off and upper-mid boost.
- Provenance: DETERMINISTIC_LOGIC, STATIC_RECIPE, PLATFORM_DERIVED.
- Rationale Represented? Hardcoded string in engineering_notes.
- Platform Dependent? Yes ("OverScream" is the AT5 TS9 emulation).

--------------------------------------------------------------------------------
2. Noise Gate Parameter Calibration
- File & Symbol: /src/services/geminiService.ts: adjustThrashPedalSelection()
- Trigger: Presence of a noise gate in the chain + thrash/high-gain context.
- Decision: Clamps Release to 120 ms, Threshold to -45 dB, and Depth to -60 dB. Converts raw numbers (0-10) to dB and ms units.
- Engineering Effect: Imposes fast gating to truncate silence on high-gain palm mutes.
- Provenance: DETERMINISTIC_LOGIC.
- Rationale Represented? Hardcoded in code comments and notes.
- Platform Dependent? Partial (formatting matches AT5 expected parameter units).

--------------------------------------------------------------------------------
3. Semantic Microphone Placement Assignment
- File & Symbol: /src/services/at5MicPlacementReasoning.ts: reasonSemanticMicPlacement()
- Trigger: Any cabinet element generated by Gemini with missing or partial mic placement.
- Decision: Assigns Position (Cap, Cap Edge, Cone, Cone Edge), Distance (Close, Medium, Far), and Angle (On Axis, 45° Off Axis) based on mic model and toneProfile gain level.
- Engineering Effect: Shapes acoustic frequency response and tames distortion fizz.
- Provenance: DETERMINISTIC_LOGIC, EXPLICIT_TT_KNOWLEDGE.
- Rationale Represented? Yes, dynamically constructed acoustic rationale string.
- Platform Dependent? No for semantic concepts; yes for final VIR mapping.

--------------------------------------------------------------------------------
4. Functional EQ Deduplication & Role Management
- File & Symbol: /src/services/at5SignalChainNormalizer.ts: filterDuplicateEqsWithRemoved()
- Trigger: Export or normalization of a signal chain containing multiple EQs.
- Decision: Categorizes EQs into pre_amp_stomp_eq, loop_eq, post_amp_rack_eq, and final_shaping_eq. Retains only the highest-ranking EQ per role; marks duplicates as SKIPPED.
- Engineering Effect: Prevents unintended cascading EQ stages in the same signal path position.
- Provenance: DETERMINISTIC_LOGIC, PLATFORM_DERIVED.
- Rationale Represented? Yes, recorded in dedupeDebugMap reasons.
- Platform Dependent? Yes (relies on AT5 stomp vs rack slot semantics).

--------------------------------------------------------------------------------
5. Single-Mic Ambiguity Auto-Routing
- File & Symbol: /src/services/at5SignalChainNormalizer.ts: detectCabSettingsFormat()
- Trigger: A cabinet has only a "Mic_1" key without schema version metadata.
- Decision: Routes the mic to primary AT5 slot "Mic_0" rather than secondary slot "Mic_1".
- Engineering Effect: Prevents a single primary mic from being exported as an unblended secondary mic.
- Provenance: DETERMINISTIC_LOGIC, PLATFORM_DERIVED.
- Rationale Represented? Yes, in CabFormatDetectionResult reason string.
- Platform Dependent? Yes (resolves 0-indexed vs 1-indexed AT5 XML slot quirks).

SECTION 10 — REASONING QUALITY OBSERVATIONS
--------------------------------------------------------------------------------

10.1 CAUSAL REASONING & HYPOTHESIS FORMATION
Current TT exhibits causal reasoning primarily in its static instructions (e.g.
"reduce bass before distortion to prevent mud") and in its deterministic microphone
placement engine (`reasonSemanticMicPlacement`). However, runtime execution does
not form hypotheses about the user's specific audio signal. It performs pattern
classification (matching text keywords to genre templates) followed by rule
application.

10.2 ALTERNATIVE SOLUTIONS & TRADE-OFFS
While `MASTER_PROMPT` requests that Gemini document amp ranking in debug text,
the system produces only a single concrete signal chain. Trade-offs (such as
loss of dynamic touch responsiveness when engaging an overdrive pedal) are
not modeled as competing objective functions or presented to the user as viable
alternatives.

10.3 OBSERVATION VS. INFERENCE VS. ASSUMPTION
Current TT frequently conflates observation with assumption:
  - Mention of the word "thrash" causes the system to *assume* the guitar needs
    a TS9-style boost with Drive 1 and Level 9, regardless of what pickups or
    playing technique are actually being used.
  - Mention of "AC/DC" causes the system to *assume* a British Lead S100 and
    forbid any overdrive pedals, even if the user is playing a low-output Stratocaster
    that might require a slight boost to reach crunch territory.

10.4 UNCERTAINTY & CONFIDENCE
The `confidence` output is an uncalibrated number. In validation recipes, it is
hardcoded to 100. In Gemini generation, it is an arbitrary integer that has no
effect on system behavior. The system does not indicate what information is
missing or uncertain.

10.5 MINIMAL INTERVENTION
Current TT demonstrates good discipline regarding minimal intervention in
vintage classic rock contexts, where it actively strips and penalizes unrequested
effects, reverbs, and EQs. In metal contexts, however, it aggressively injects
noise gates and overdrive pedals deterministically.

10.6 WHOLE-CHAIN REASONING
Whole-chain interaction is respected in the fixed ordering rules (pre-gain vs
post-gain) and in the dual-mic placement engine (Mic 2 placement adjusts to
complement Mic 1). However, complex interactions (such as power amp sag altering
preamp tone stack responsiveness) are not modeled.

10.7 ITERATIVE EVALUATION
Completely absent. The pipeline is purely feed-forward: Input -> Prompt -> JSON ->
Deterministic Overrides -> Export. There is no feedback loop to test or refine
the generated preset.

SECTION 14 — FACTUAL BASELINE FINDINGS
--------------------------------------------------------------------------------

The audit establishes the following objective facts regarding Current TT:

1. Current TT contains high-quality, explicit acoustic knowledge in its
   Semantic Microphone Placement Engine (/src/services/at5MicPlacementReasoning.ts).
   This module reasons from acoustic transducer principles (proximity effect,
   off-axis dispersion, cone breakup) to assign 4D mic placements.

2. Critical tone-shaping decisions are made deterministically AFTER Gemini has
   finished generating. In thrash and high-gain contexts, TypeScript code
   overrides boost pedals to OverScream, sets Drive and Level, clamps Noise Gate
   parameters, and overwrites engineering notes.

3. Current TT uses static recipes that completely bypass AI reasoning for prominent
   test cases (AC/DC Malcolm Young, Pantera Cowboys From Hell, Metallica Kill 'Em All)
   when validation mode is enabled, and in Tone Profile classification.

4. Current TT does NOT perform audio DSP feature extraction. The nine audio
   feature fields in `ToneProfile` are explicitly wiped to `undefined` upon parsing.

5. Current TT accepts a user recording ("Your Recording") in the UI, but completely
   drops it before making the Gemini API call. The user recording has zero influence
   on generated tone.

6. Current TT's sound engineering concepts are heavily coupled to AmpliTube 5.
   Prompts, normalizers, and directories are constructed around AT5 gear names,
   AT5 parameter names, and AT5 hardware limitations (such as the 2-band Parametric EQ).

7. Current TT signal chains are strictly serial. There is no representation or
   reasoning for parallel paths, dual-amp rigs, or wet/dry/wet topologies.

8. Current TT contains extensive domain contract skeletons created in Phase 1B
   (EvidenceRecord, EngineeringDecisionRecord, SemanticToneDesign), but these
   contracts are currently unexercised by the live tone translation engine.

9. Current TT has no iterative evaluation or feedback loop. It cannot test its
   own generated presets, observe results, or refine its output.
